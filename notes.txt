  The "wiring" in plain English:

  1. Cloudflare DNS → maps domain names to destinations. Just a phone book — "rkteambuilder.com goes to CloudFront"
  2. ACM Certificate → proves you own the domain. CloudFront uses it for HTTPS. Validated by adding a CNAME in
  Cloudflare.
  3. VPC → your isolated network. Nothing gets in or out unless you explicitly allow it.
  4. Subnets → sections within your VPC. Public subnet has an Internet Gateway (EC2 lives here). Private subnets have no
   internet (RDS lives here).
  5. Route Table → traffic rule: "outbound traffic from public subnet → goes through Internet Gateway." Private subnets
  don't have this rule, so they're isolated.
  6. Security Groups → firewalls on individual resources. EC2 only accepts SSH from your IP and HTTP from CloudFront.
  RDS only accepts PostgreSQL connections from EC2.
  7. IAM Role → permissions for EC2. Instead of storing AWS credentials on the server, the role lets EC2 access specific
   services (Parameter Store, ECR, etc.) automatically.
  8. CloudFront → sits between users and your infrastructure. Routes /auth/*, /teams/* etc. to EC2, and everything else
  to S3. Adds HTTPS, caching, DDoS protection.
  9. S3 Bucket Policy + Referer secret → only CloudFront can read frontend files. Direct S3 access is blocked.
  10. Nginx + Origin secret → only CloudFront can reach EC2's API. Direct EC2 access is blocked.

  The key security principle: Users only talk to CloudFront. CloudFront proves its identity to both S3 (referer secret)
  and EC2 (origin secret). EC2 proves its identity to RDS (security group). Everything else is locked down.


1. Why security groups and IAM roles?

  Think of them as two different kinds of locks:

  - Security groups = physical locks on doors. "Who can physically reach this machine, and on which port?" Without them,
   anyone on the internet could try connecting to your database directly.
  - IAM roles = ID badges. "Once you're inside, what are you allowed to do?" Your EC2 needs to pull Docker images and
  read secrets — the role says "you can do these specific things, nothing more."

  Why both? A security group lets CloudFront reach EC2 on port 80, but that doesn't mean EC2 should be able to delete
  your S3 bucket. The IAM role limits what EC2 can do with other AWS services.

  The port numbers and subnet CIDRs — you don't need to memorize them. They're just addresses. 10.0.1.0/24 means "256
  addresses starting at 10.0.1.0". Public subnet gets one range, private subnets get another. That's it.

  2. Why Nginx and X-Origin-Verify?

  The security group allows traffic from any CloudFront IP. But anyone can create a CloudFront distribution — not just
  you. So a bad actor could set up their own CloudFront pointing to your EC2 and bypass your setup.

  Nginx checks a secret header (X-Origin-Verify) that only your CloudFront distribution sends. No secret = 403 rejected.

  Nginx also acts as a reverse proxy — it sits in front of FastAPI and handles things like timeouts and header
  forwarding. FastAPI shouldn't be directly exposed.

  3. Why so complicated? Why not needed locally?

  Locally, everything runs on localhost:
  - Only you can access it (your laptop isn't on the public internet)
  - No one is trying to hack it
  - No HTTPS needed (browsers trust localhost)
  - No DNS needed (localhost just works)
  - No CDN needed (you're the only user, sitting next to the server)

  In production, you're exposing your app to the entire internet. The complexity comes from three things:

  ---
  Phase 3: Backend -- Quota and Rate Limit Gauntlet

  Before any LLM call happens, the endpoint runs a series of checks (main.py:4113-4177):

  1. Team hash (line 4102): Generates an MD5 hash of the team composition (monsters + moves + magic item, but NOT
  personality/talent). This is language-independent.
  2. Cache pre-check (line 4105): check_if_all_cached() checks Redis for all 7 cache keys (6 monster + 1 team). If
  everything is cached, the entire quota/rate-limit gauntlet is skipped -- cached results are free.
  3. If not fully cached, the checks are:
    - Retry grace: If a previous analysis partially failed and grace was granted, this bypasses quota
    - Per-user quota: Anonymous users get 1/day, guests 3/day, free 5/day, premium 20/day (configurable in
  tier_limits.py)
    - Cross-account device cap: Max 5 analyses/day per physical device regardless of account switching
    - IP daily cap: Fallback when device_id is unknown (15/day)
    - Global IP rate limit: Prevents rapid-fire analyses from same IP
    - Per-team rate limit: Prevents re-analyzing the same team by switching languages

  ---
  Phase 4: Backend -- The Core Analysis (main.py:3540-4056)

  Step 1: Load data from PostgreSQL (lines 3584-3643)

  Batch-loads into dictionaries via SQLAlchemy:
  - All 6 monsters from the monsters table
  - All unique moves from the moves table
  - All traits for these monsters from the traits table
  - ALL types (with eager-loaded type effectiveness relations)
  - All personalities, the magic item, and all game terms

  Step 2: Build 7 LLM tasks (lines 3651-3817)

  For each of the 6 monsters:
  1. Resolves which game terms are actually referenced in that monster's trait and move descriptions using
  reference_resolver.py (BFS traversal, depth 3) -- this keeps prompts focused and smaller
  2. Generates a Redis cache key: llm_cache:monster_trait:{md5(monster_id + sorted_move_ids + language)}
  3. Builds a prompt via build_trait_synergy_prompt() (line 523) asking the LLM to analyze synergies between the
  monster's trait and its 4 selected moves, given the type chart and game terms
  4. Creates an async call_llm() task

  For the team overall (the 7th task):
  1. Resolves references across ALL traits + moves + magic item
  2. Cache key: llm_cache:team_synergy:{md5(magic_item + all_monster_keys + legacy_types)}
  3. Builds a prompt via build_team_synergy_prompt() (line 746) asking for team archetype, action priority, switching
  strategy, magic item usage, and overall strategy

  Step 3: Execute concurrently (line 3820)

  llm_results = await asyncio.gather(*llm_tasks, return_exceptions=True)

  All 7 LLM calls run in parallel.

  ---
  Phase 5: LLM Service and Cache Layer

  llm_service.py:282-418 -- generate_analysis_json():

  Each of the 7 tasks goes through this function, which delegates to the cache layer.

  cache.py:201-293 -- RedisCache.get_or_compute():
  1. Check Redis for the cache key -- if hit, return immediately (no LLM call)
  2. If miss: acquire a distributed Redis lock (stampede protection -- prevents 10 concurrent requests from all hitting
  the LLM for the same key)
  3. Double-check cache after getting the lock (another request may have filled it)
  4. If still miss: call the LLM provider
  5. Store result in Redis with 1-hour TTL
  6. Release lock

  LLM providers (llm_service.py):
  - Gemini (lines 98-155): Uses genai.Client with thinking mode enabled (up to 24K thinking tokens), requests JSON
  response format
  - DeepSeek (lines 157-267): Uses OpenAI-compatible async client with response_format: json_object

  Both return a parsed JSON dict + metadata.
